# NewCo commodity-trading corpus: generator

`BRIEF.md` is the specification. This README covers how to run the generator, the manifest keys, and
the decisions taken while building it. Nothing here calls AWS or the network.

## Added phases

Three phases follow the brief's four. Each has its own counts in `build.EXPECTED_TOTALS`, its own manifest key and
its own tests, and none changes a byte of the earlier phases.

| Phase | What it tests | Ground truth (manifest key) | Tests |
|---|---|---|---|
| `docsets` | Cargo document sets for multi-product deals. `d1`: five batches from four senders as DOCX, text PDF, scanned image-only PDF and XLSX; everything reconciles. `d2`: one merged 23-page PDF holding 12 documents, blank separators in some places only, scanned pages; a missing third original B/L and an invoice quantity that is not the B/L quantity. | `docsets[]`: the deal (quantity ranges, fixed and formula prices, documents clause), logical documents with file and page range, a page map per file, and the reconciliation (counts per requirement, quantities against ranges and each other, prices against the formula, invoice arithmetic, exceptions) | `test_fsi_docsets.py` |
| `lifecycle` | A master agreement from draft to use. One file name carries three revisions; forwards and a "clean" return repeat two of them; terms move in tracked changes, Word comments and email bodies; quoted history repeats superseded terms; internal credit and business instructions are not offers; one email is resent; legal, credit and business approve; the executed copy is a scan; an amendment is signed before it takes effect. Netting, late interest, a margin call and the renewal notice deadline then use the term in force on the right date. | `lifecycle`: a clause event timeline (status, source, message, attachment hash, effective date), revisions by hash, comments, forwards, duplicates, approvals and calculations. `lifecycle/common.py` `terms_as_of` answers "on the table" and "agreed and in effect" at any moment. | `test_fsi_lifecycle.py` |
| `execution` | Bloomberg shorthand and ETRM bookings. Twelve historical chats across three trader pairs end in confirmed bookings in a RightAngle-style CSV export; the same tokens mean different things per pair (`k` is kbbl for Houston/Vitol, kt for London/BP; `+n` is cents per bbl or dollars per mt). Six new chats are read with confidence learned from the pair's own confirmed history; a pair with no history goes to review. Email confirmations are the binding record; the ETRM export carries four breaks (side, product, unit, premium); three are caught and amended to version 2, one stays open. | `execution`: dialects, history, per-token interpretation with evidence and confidence, confirmations, every ETRM row and version, and breaks with status | `test_fsi_execution.py` |

New writers: `writers/xlsx_writer.py` (SpreadsheetML), `writers/pdf_tools.py` (page merge with blank pages, and seeded
raster scans with no text layer) and comments in `writers/docx_writer.py`. Scan and merge bytes depend on the pinned
`pypdfium2` and `pillow` versions in `requirements.txt` and `uv.lock`. `Scenario.send` takes `forward_of` (a `Fwd:`
subject and `References` without `In-Reply-To`); `Desk.mail` takes `fwd` and `quote`.

## Run

From the repository root. The pins for Faker and ReportLab are in the root `pyproject.toml` dev group and `uv.lock`, so `uv run --frozen` needs nothing else:

```bash
uv run --frozen python -m tests.benchmark.fsi_commodity                                  # write corpus/ and golden_answers.json
uv run --frozen python -m tests.benchmark.fsi_commodity --check                          # exit 1 if anything differs from a fresh build
uv run --frozen python -m tests.benchmark.fsi_commodity --scenario s1-houston-vitol-wti  # one scenario plus universe.json
uv run --frozen python -m tests.benchmark.fsi_commodity.replay                           # offline replay against the manifests
uv run --frozen python -m tests.benchmark.fsi_commodity.golden                           # rewrite golden_answers.json (--check to verify)
uv run --frozen pytest tests/unit/benchmark_fsi
```

Without `uv`: `python -m pip install -r tests/benchmark/fsi_commodity/requirements.txt`, then the same `python -m` commands.

Options of the main command: `--scenario ID`, `--check` (exit 1 on any missing, extra or changed file, including `golden_answers.json`), `--out DIR`, `--seed N`. `replay` takes `--corpus DIR` and `--phase PHASE`.

## Decisions

| Decision | Reason |
|---|---|
| Faker 40.63.0 and ReportLab 5.1.1 are pinned in the root `pyproject.toml` dev group and `uv.lock`; run with `uv run --frozen`. `requirements.txt` stays as a pip fallback for shells without `uv` and repeats the same pins (plus `tzdata` and `PyYAML`). | The orchestrator added the pins and relocked after the foundation phase. `tzdata` is needed because Windows has no system zone database for `zoneinfo`. The file must be kept in step with the lock. |
| DOCX is written by hand with `zipfile`, not a library. Tracked changes are `w:ins` / `w:del` runs. Members use a fixed timestamp, fixed order, fixed `create_system` and `ZIP_STORED` (no compression). | python-docx has no tracked-change API and stamps archive members with the wall clock. Stored members keep bytes independent of the zlib build; the plan said `ZIP_DEFLATED`, this is stricter for determinism. |
| PDF: ReportLab platypus with `invariant=1`, `pageCompression=0`, built-in fonts, no images. | `invariant=1` pins the creation date and document id, so the PDF info date is not the scenario date. The scenario date is printed in the document body. |
| Faker is one cached instance per locale, re-seeded with `seed + crc32(key)` before every entity or person. Faker supplies names, street numbers and phone numbers only. Identifiers come from `ids.py`. | Seeding per key keeps every entity independent of the others (tested by adding a counterparty). `crc32`, never `hash()`, because `hash()` is salted per process. |
| `.eml` is written with `policy.default` and `\n` line endings; the MIME boundary is derived from the Message-ID. `corpus/** -text` in `.gitattributes`. | Random boundaries and `autocrlf` both break byte-identical builds. |
| Message-ID is `<sha1(scenario|key)[:20]@sender-domain>`. `In-Reply-To` is the parent's id; `References` is the parent's `References` plus the parent's id. | Stable and reproducible. |
| Send times: each message lands inside the sender's local working hours (09:00 to 17:30) on a business day of the sender's calendar, 7 to 90 minutes after the previous message, or `after_business_days` later. Chats step by 20 to 240 seconds. | Brief section 4. Holiday lists are our own and cover 2025 and 2026 only; other years raise `ValueError`. |
| The corpus year-range limit (2025 to 2026) applies to calendars only. | Keeps holiday data small and checkable. |
| `universe.json` ids: `newco-*`, `cp-*` (counterparties), `hold-*` (holding and trust entities), `bank-*`, `svc-*`, `own-*` (natural-person owners). Person ids are `p-<org>-<role>`. | Stable keys for later phases and the structured tables. |
| Besides the brief's four real-name counterparties, `cp-bp-au` (BP Australia Pty Ltd, owned 100% by BP Oil International Limited) is the BP entity that NewCo Sydney deals with in `s5`. | The brief says "BP, Sydney (via London)" and "second NewCo entity relies on London's KYC", which needs a Sydney-side BP entity. |
| Ownership edge classes: a legal-entity parent holding more than 50% gets `DirectConsolidation`, or `UltimateConsolidation` when that parent has no legal-entity parent of its own. Edges from natural persons and holdings of 50% or less carry no class. | GLEIF L2 relationship classes apply between legal entities. |
| Beneficial owners are natural persons whose effective share (product along each path, summed over paths) is at least 25%. Founders: 55% and 45% of a partnership that holds 62%, giving 34.1% and 27.9%. | Brief section 2. |
| PEP: `own-kestrel-pep` (3 hops from Kestrel). Sanctioned: `own-tiber-hidden` (4 hops from Tiber Peak). Both belong to fictional counterparties and the build raises if a flag sits on anyone tied to a real-name party. | Brief section 8. |
| `ontology.cls(name, within)` raises `KeyError` for unlisted classes and for ambiguous names (`LegalEntity`, `Account` exist in more than one ontology; pass `within="gleif"` or `"fibo"`). `wasDerivedFrom` and `wasAttributedTo` are PROV properties, stored as relation names next to the `prov#Entity` class. | The generator may not invent classes. |
| Section names follow BRIEF section 4 (`trade/`, `post_trade/`, `settlement/`), not the `deals/` and `post/` names in section 10. Corpus folders are `onboarding`, `trade`, `post-trade`, `settlement`. | The registry tuples (`ONBOARDING`, `TRADE`, `POST_TRADE`, `SETTLEMENT`) match section 4. |
| `--scenario ID` builds every phase in memory and writes that scenario plus `universe.json`. An unknown id exits 2. | Later phases read earlier ones. |
| `build()` enforces each scenario's `expect` counts and, once a phase has six scenarios, the brief's phase totals. | Counts must equal the brief. |
| `--check` reports `missing`, `extra` and `changed` (SHA-256), only inside the phase folders and top-level entries the generator owns. | Does not flag files the user adds elsewhere in `corpus/`. |
| Unit tests live in `tests/unit/benchmark_fsi/` and carry `pytestmark = pytest.mark.unit`. File names are prefixed `test_fsi_` because `tests/unit` has no `__init__.py`, so basenames must be unique. | Follows `tests/unit/test_unit_marker_coverage.py`. |
| File count: the brief's totals (269 emails as `.eml` and `.md`, 171 attachments, 13 chats) give about 720 files. | The brief's counts win. |
| Onboarding: each scenario module `onboarding/sN_*.py` exposes `build(u, upstream)` and `EXPECT`, and registers in `ONBOARDING`. `onboarding/common.py` holds `Desk` (addresses mailboxes as `org-id:role`), the KYC, credit and SSI document builders, `Negotiation` (tracked-change rounds built with `clauses.redline_rounds`) and `onboarded(u, upstream=None)`. | `onboarded()` lives in `onboarding/common.py` as the plan's step 7 says; `trade/common.py` will import it (BRIEF section 4 names `trade/common.py`). Each scenario stores its record in `Scenario.data["onboarded"]` (agreement name, clause values, payment days, tolerance, governing law, credit tiers, limit, exposure, headroom, effective date, account ids, scenario extras). |
| Planted problems are spread so that `s1` is a clean control: `s2` questionnaire denies a PEP that screening finds (caught); `s3` stale good-standing certificate, SBLC that expires before the trading period ends, and an email that disagrees with its redline (none caught); `s4` alias "Glencore Limited" and a qualified netting opinion summarised as clean (not caught); `s5` reliance on a stale London KYC file (not caught); `s6` hidden 60% sanctioned owner (caught, decline). This split gives every scenario at least one problem except the control. |
